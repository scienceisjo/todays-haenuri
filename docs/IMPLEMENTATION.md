# 구현 구조 (v1.0 — GitHub Pages + Supabase)

- 화면: `public/app.js`(단일 SPA) → `public/lib/data.js` 만 호출. 순수 규칙은 `lib/core.js·series.js·import.js`.
- 데이터: Supabase Postgres. 표·정책·함수는 `supabase/schema.sql`. 권한은 RLS(`is_active_staff / is_admin / my_department`)와 security definer 함수가 검사. 조회는 `records_view / duties_view / activity_logs_view`(security_invoker) 사용.
- 반복 일정: 회차마다 개별 records(series_id) — `create_series` 함수가 원자적으로 생성, `update_record / delete_record` 가 scope(single/following/all)·version 을 처리.
- 일괄 등록: 브라우저가 파일을 읽고 미리 보기 검증(`lib/import.js`) → `import_duties / import_schedule` 함수가 다시 검증해 한 트랜잭션으로 저장.
- 첨부: Storage 비공개 버킷 `attachments`, 경로 `<record>/<id>.<ext>`, 정책이 `can_view_record / can_edit_record` 로 검사. 화면은 서명 URL(5분)로 열람·내려받기. 새 안내+첨부는 초안→업로드→확정(원자적 게시) 유지.
- 로그인: Supabase Auth. `auth.users` insert 트리거 `handle_new_user` 가 명단(roster)·관리자 이메일 규칙으로 staff 행 생성. 비활성(active=false)은 RLS 에서 모든 접근 차단.
- 배포: `public/` 을 GitHub Pages 로. 상대 경로·`<meta>` CSP·vendor supabase-js·scope 기준 서비스워커.

아래는 v0.x(Node+SQLite, `_legacy/`) 시점의 문서이며 화면 규칙(급식지도 두 자리, 공개 조건, 시간대, 월간표, 일괄 등록 검증 규칙, 반복 규칙)은 그대로 유효하다.

# 구현 구조와 확정한 동작

## 범위

v0.1.0은 클로드 인계를 위한 독립 실행 소스 초안이다. 배포와 외부 계정 등록은 수행하지 않았다.
서버는 Node.js 24 내장 HTTP, `node:sqlite`를 사용한다. UI는 빌드 없는 ES module이다.
학교의 기존 소스 저장소나 외부 배포 프로젝트를 변경하지 않았다.

종류마다 별도 테이블을 무조건 두지 않고 날짜·게시 기간·파일·작성자 동작을 공유했다.

업로드 파일은 공개 정적 경로에 저장하지 않는다. 요청할 때 인증·게시 대상·작성 권한을 확인한다.
초기 버전은 로컬 디스크 파일 저장소다. 후속 중앙 배포에서 영구 디스크 또는 객체 저장소로 교체 가능하다.

## 계정과 권한

- 공개 회원가입은 없다. setup으로 첫 관리자를 만들고 관리자가 나머지 계정을 추가한다.
- 기본 세션은 12시간. 개인 컴퓨터 로그인 유지를 선택하면 7일.
- 토큰은 HttpOnly/SameSite=Lax 쿠키에, 서버에는 토큰 해시와 만료를 저장한다.
- 쓰기 API에는 정확한 Origin과 CSRF 토큰을 검사한다.
- 비밀번호는 개별 salt와 scrypt(N=32768, r=8, p=1)로 해시한다.
- 일반 교직원은 자신의 레코드만 수정/삭제하고 관리자는 모두 수정한다.
- 일반 대시보드에는 공개 조건을 만족하는 안내만 나온다. 작성자·관리자는 관리 화면에서 임시·예약·종료된 자신의 관리 대상도 읽는다.
- 부서 제한 첨부파일은 허용 부서, 작성자 또는 관리자만 읽을 수 있다.
- 계정 비활성화·관리자 권한 변경·관리자의 비밀번호 재설정 시 세션을 해제한다.
- 읽음 표시는 특정 버전에 대한 확인이다. 본문이나 첨부를 변경하면 다시 확인할 수 있다.
- 초기 관리자 비밀번호 입력은 터미널 echo를 사용한다. 후속 개발에서 마스킹 입력으로 개선 가능하다.

## 시간과 예약

날짜는 `YYYY-MM-DD`의 한국 날짜로 저장한다. 시각은 timezone을 명시해 UTC ISO 문자열로 저장한다.
일정 시간은 한국 시간의 `HH:mm`. 브라우저 PC 시간대가 다른 경우에도 입력값은 `+09:00`으로 변환한다.

공지 공개 조건:

1. 삭제되지 않음
2. state=published
3. publish_at <= 서버 현재 시각
4. expire_at이 없거나 서버 현재 시각 < expire_at
5. 대상 부서 조건을 만족함

예약은 조회 시 서버가 판단한다. 브라우저 타이머만으로 숨기지 않는다.
열린 화면은 30초 간격, 활성화·온라인 복귀 시 갱신한다. 즉시 실시간 push는 아직 없다.
급식과 급식지도는 한국 날짜가 바뀌거나 날짜 선택을 변경하면 해당 날짜 자료를 보여준다.

## 급식지도

`meal_duties.date`에는 UNIQUE를 적용한다.
`entrance_staff_id`, `inside_staff_id`는 실제 사용자 FK이며 서로 달라야 한다.
각 자리를 아직 지정하지 못한 경우 NULL을 허용해 화면에 '담당자 미지정'으로 보여준다.
현재 재직 중인 계정만 새로 지정할 수 있다.
대체 인력은 해당 필드의 현재 담당자를 바꾸고 note에 변경 이유를 적는다. 별도 세 번째 자리를 만들지 않는다.
예약 자료는 게시 전 작성자·관리자에게만 반환하며 그 화면에 예약 표시가 붙는다.
주간 화면에서 자신의 예약 지도를 열고 수정할 수 있다.
월간표(`dutiesView`)는 수업일(월~금) 한 달을 표로 보여주고, 주말은 지도가 등록된 경우에만 표시한다.
날짜별로 '식당 입구/식당 내부' 두 자리를 나열하고, 미지정·예약 건수를 집계하며 '담당자가 빈 날짜만 보기'로 거를 수 있다.
빈 날짜의 '담당자 지정'은 그 날짜를 채운 등록 폼을 연다. 표시 자료는 bootstrap이 돌려주는 범위(공개분 + 본인 예약, 관리자는 전체)를 따르며, 저장 권한은 서버가 다시 검사한다.

## 일괄 등록 (CSV·엑셀)

`server/import.mjs`가 파일 → 표 → 열 매핑 → 행 검증 → 저장을 맡는다. 외부 라이브러리는 쓰지 않는다.

- **읽기**: UTF-8 BOM·UTF-8·CP949(`TextDecoder('euc-kr')`)·UTF-16LE를 순서대로 시도하고, 구분자(쉼표·탭·세미콜론)는 첫 줄에서 고른다. `.xlsx`는 ZIP 중앙 디렉터리를 직접 읽고(`zlib.inflateRawSync`) `xl/sharedStrings.xml`과 첫 시트를 정규식으로 파싱한다. 숫자 셀은 숫자로 남겨 두어 날짜 일련번호(1899-12-30 기준)와 시간 분수를 변환한다. ZIP64·암호화·.xls는 지원하지 않고 안내 문구로 거절한다.
- **열 매핑**: 머리글을 정규화(공백·괄호·기호 제거, 소문자)해 `HEADERS`의 별칭과 맞춘다. 필수 열이 없으면 읽은 머리글을 함께 보여주며 실패한다.
- **교직원 해석**: 재직자 목록에서 이름(공백 무시)으로 찾고, 여러 명이면 `이름(부서)`·`이름·부서`·`이름/부서`의 부서명으로 좁힌다. 이메일과 사용자 ID도 허용한다. 해석 실패는 행 오류로 남기고 후보 표기를 안내한다.
- **미리 보기**는 DB를 바꾸지 않는다. 행마다 errors·warnings·existing(기존 자료 요약과 수정 가능 여부)·empty(건너뜀)를 돌려주고, 요약(총·정상·오류·건너뜀·중복)을 붙인다.
- **저장**은 클라이언트가 돌려준 행을 서버가 처음부터 다시 검증한다(교직원 재직 여부, 날짜, 같은 사람, 파일 안 중복, 기존 자료 권한). 오류가 하나라도 있으면 기본은 400으로 거절해 아무것도 저장하지 않고, `skip_invalid`일 때만 오류 행을 제외한다. 저장은 하나의 트랜잭션이며 activity_logs에 건수를 남긴다.
- 급식지도 중복 기준은 날짜(UNIQUE), 학사 일정은 삭제되지 않은 같은 유형+제목+날짜다. 갱신은 작성자·관리자만 가능하고 version을 올린다. 갱신 시 기존 안내의 게시 상태·부서·열람 대상은 유지하고 제목·내용·날짜·시간·장소·중요도만 바꾼다.
- 휴업일 행은 관리자만 저장할 수 있으며 records가 아닌 holidays에 들어간다.

## 반복 일정과 휴업일

반복은 규칙을 저장해 조회 때 펼치지 않고, **등록 시점에 회차마다 개별 레코드로 펼쳐 저장**한다(`series_id`, `series_index`). 그래서 대시보드·달력·주간·읽음·첨부·권한 로직을 바꾸지 않았다. 규칙 원본은 `record_series.rule`에 남긴다.

- `series.mjs`의 `occurrences()`: 매주는 시작 주의 일요일을 기준으로 간격(주)마다 선택 요일을 나열하고, 매월은 시작일과 같은 날짜를 고르되 그 날짜가 없는 달(31일 등)은 건너뛴다. `until` 또는 `count`(최대 200)로 끝내고, 어느 쪽이든 2년을 넘지 않는다. `skip_holidays`면 holidays에 있는 날짜를 뺀다. 여러 날짜에 걸친 일정은 시작-종료 간격을 회차마다 유지한다.
- 회차 하나의 수정·삭제는 일반 레코드와 같다. `scope=following`은 같은 시리즈에서 그 회차 날짜 이후(삭제되지 않은) 회차, `scope=all`은 시리즈 전체에 적용한다. 다른 회차에는 날짜·게시 시각·게시 종료를 제외한 내용 필드만 복사해 **각 회차의 날짜를 보존**한다. 낙관적 잠금은 클릭한 회차에만 적용하고 나머지는 version만 올린다.
- 반복 등록에는 첨부를 붙일 수 없다(첨부 원자적 게시 흐름과 섞이지 않도록). 회차를 열어 개별로 첨부한다.
- 휴업일은 관리자만 관리한다(학교 전체 설정). 급식지도 양식 생성, 반복 생성, 월간표의 미지정 집계에서 제외되고 달력·미니 달력·주간·월간표에 표시된다.

## 브랜딩(앱 이름·로고)

- 앱 이름은 `settings.app_name`이며 `branding()`이 /api/info·/api/bootstrap에 함께 돌려준다. 화면은 사이드바·홈 메뉴·로그인·document.title에 이 값을 쓰고, /manifest.webmanifest는 정적 파일을 바탕으로 이름·설명·아이콘을 채워 동적으로 응답한다.
- 로고 파일은 `DATA_DIR/branding/logo.png|svg`에 두고 settings에 파일명·MIME·PNG 크기·버전을 기록한다. `/logo`는 로그인 전 화면에도 필요하므로 공개 경로이며, 파일이 없으면 public/icon.svg를 준다. 업로드는 관리자만, PNG는 서명과 IHDR 크기를 읽고 SVG는 `<script>`·이벤트 속성·외부 요소가 있으면 거절한다. SVG 응답에는 sandbox CSP를 붙여 직접 열어도 스크립트가 돌지 않는다.
- 정사각형 192px 이상 PNG일 때만 manifest 아이콘으로 쓴다(Edge 설치 아이콘 요건). 그 외에는 기본 PNG 아이콘을 유지한다.
- `logo_version`(업로드·삭제 시 갱신)을 `/logo?v=`에 붙여 브라우저 메모리 캐시를 우회한다.
- 프로젝트 `branding/` 폴더의 logo.png/svg는 `installBundledLogo()`가 데모 시드와 운영 설치 때 복사한다. 이미 운영 중인 서버는 화면에서 올린다.

## 충돌과 파일 저장

레코드, 급식, 급식지도 수정에는 version을 제출해야 한다. 현재 버전과 다르면 409를 반환한다.
DB UNIQUE와 CHECK도 함께 적용해 화면을 우회한 중복 저장을 막는다.
레코드 삭제는 soft delete라 관리자가 복구할 수 있다. 급식/지도/첨부 삭제는 현재 물리 삭제다.

파일은 허용 확장자만 받으며 1개 10MB 이하다. 임의의 UUID 파일명으로 저장한다.
PDF/PNG/JPEG/WebP는 서명 일부를 확인한 형식만 inline으로 제공한다. 이는 악성 파일 검사 전체를 대신하지 않는다.
HWP/HWPX/XLS/XLSX/DOC/DOCX/TXT/CSV는 원본 다운로드를 제공한다. 이들 형식의 문서 변환/미리 보기는 구현하지 않았다.

첨부가 있는 새 안내는 원자적으로 게시한다. 먼저 비공개 초안(state=draft)으로 저장하고, 모든 파일을 올린 뒤, 마지막에 목표 상태(published/예약)로 확정 PATCH를 보낸다.
따라서 업로드가 중간에 실패해도 본문이 첨부 없이 먼저 공개되지 않는다. 실패 지점에서 다시 저장을 누르면 남은 파일만 이어 올리고 게시를 확정한다.
중복 방지: 초안 생성은 한 번만(`dataset.savedId`), 파일은 이름·크기·수정시각 키로 건너뛰며(`dataset.uploaded`), 확정은 한 번만(`dataset.finalized`) 실행한다.
첨부 업로드 응답은 갱신된 레코드 version을 돌려주어, 확정 PATCH가 정확한 version으로 낙관적 잠금을 통과한다.
수정(기존 안내) 시에는 본문 PATCH 후 남은 첨부를 올리는 기존 흐름을 유지한다. 이미 공개된 안내이므로 '본문 먼저 공개' 문제는 발생하지 않는다.
임시저장 자체(state=draft로 저장)는 처음부터 비공개이므로 확정 단계 없이 파일만 올린다.

## 오프라인·백업

Service Worker에는 공개 정적 화면만 캐시한다. API·첨부파일 응답은 캐시하지 않는다.
이미 열린 창에서 네트워크가 끊기면 메모리에 있는 마지막 자료와 경고를 표시한다.
오프라인 상태에서 페이지를 새로고침하면 마지막 업무 자료를 다시 복구하는 기능은 없다.
로그아웃 또는 인증 만료 시 화면의 사용자 업무 데이터를 지운다.

JSON 내보내기는 자료 확인용이며 완전한 백업이 아니다. 비밀번호·세션·첨부파일 바이트는 포함하지 않는다.
완전한 백업은 서버를 정지하고 운영 데이터 폴더 전체를 복사하거나, SQLite 백업 API와 uploads를 함께 보존해야 한다.
자동 백업과 앱 내 복구 기능은 아직 구현되지 않았다.

## 개발 시 유의점

- DOM에 삽입되는 사용자 문자열은 h()를 통과하고, 외부 링크는 http/https만 허용한다.
- 동적 SQL의 테이블·컬럼명은 코드 내부의 허용 목록으로 제한한다.
- 비밀번호와 로그인 토큰을 로그·내보내기 파일·실제 샘플 데이터에 넣지 않는다.
- DATA_DIR를 서버의 public 경로로 지정하지 않는다.
- 운영 중앙 서버에서는 HTTPS와 `COOKIE_SECURE=true`, 정확한 APP_ORIGIN을 구성한다.
- 추가 마이그레이션은 `server/migrations/NNN_이름.sql`로 두면 db.mjs가 번호 순서대로 자동 적용한다. 운영된 001·002 스키마를 덮어쓰지 않는다.
